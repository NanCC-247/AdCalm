# 曝光与反馈计划

版本：v0.1.1-beta.1。目标是在一轮小规模公开测试中获得 **10–20 名愿意提供可复现反馈的测试者**，检验下载、启用和日常操作流程。人数是计划目标，下载量和使用效果均不作保证。

## 已准备的入口

| 入口 | 用途 |
|---|---|
| [README](../../README.md)首屏 | 固定版本 APK 下载、兼容范围、默认观察与文档入口。 |
| [Release](https://github.com/NanCC-247/AdCalm/releases/tag/v0.1.1-beta.1) | 正式签名 APK、SHA-256、签名证书指纹、测试记录和脱敏分享素材。 |
| [问题模板](https://github.com/NanCC-247/AdCalm/issues/new/choose) | 结构化记录版本、系统、模式、增强开关与复现步骤。 |
| [自荐草稿](首发自荐文案.md) | V2EX 和酷安的开发者自荐内容，由用户核对后发布。 |
| [隐私说明](../privacy.md)与[安全使用说明](../guides/安全使用说明.md) | 操作选择、暂停、文件恢复和分享数据范围。 |

## 首轮执行顺序

1. **发布当天：** 从未登录 GitHub 的浏览器验证 Release 链接和 APK 下载，核对安装与校验说明。选择已脱敏素材，在允许自荐的社区位置公开说明开发者身份与 Beta 状态。
2. **前 3 天：** 在自荐帖回复安装、权限与观察模式问题，将可复现场景整理为 Issue。漏识别、误点、回退和文件处置分别记录，邀请测试者先以少量应用观察。
3. **约第 7 天：** 汇总实际测试者数、系统范围、可复现问题和仍缺少的样本。发布小幅修复或公开结果摘要，每项结果带版本与证据范围。
4. **下一轮：** 依据实际反馈决定继续 Beta、缩小功能范围或补充验证。与首批反馈闭环后再扩大曝光。

本计划不自动代发帖子或私信，不要求注册额外反馈账号，也不收集联系方式或设备唯一标识。社区发帖时再次核对其当前规则；没有合适版块时先调整内容与入口。

## 测试者最小反馈清单

- AdCalm 版本、机型、Android 和厂商系统版本。
- 能否下载、安装、启用无障碍，是否了解默认纯观察。
- 当时所选范围、自动/观察模式、增强开关及相关权限状态。
- 一段可重复的操作步骤、预期行为、实际结果。
- 可选：已检查过的脱敏摘要或遮盖后的相关截图；原始诊断保留本机。

对耗电、后台存活或成功率有疑问时，先明确对照条件与观测时间，再记录测量。单次跳过演示、点击计数或某台设备的结果不扩展成全体设备结论。

## 反馈处理

| 场景 | 首先处理 | 发布时说明 |
|---|---|---|
| 误点、影响正常任务、数据移动异常 | 建议暂停相关功能，复现并核实触发条件，必要时降低默认能力或暂停该功能。 | 受影响版本、场景、修复及仍未验证的范围。 |
| 无法安装、权限流程失败、后台失效 | 按系统和构建签名分类，补充可复现步骤。 | 实际兼容条件，避免宣称全 ROM 保活。 |
| 漏识别 | 收集最小场景和正常页面负样本。 | 已验证的触发条件，避免承诺某平台全面适配。 |
| 隐私、素材或权利反馈 | 核实公开内容与实际功能，及时遮盖、替换或修正。 | 不继续转发涉私人信息的附件。 |

## 如何判断有用

每轮记录 Release 附件下载次数、提供有效反馈的测试者数、可复现 Issue 数和已闭环问题。GitHub 下载次数不等于独立用户或安装成功；Star 只作为关注信号。维护者可公开汇总系统范围与问题结果，避免发布测试者身份、联系方式、完整应用清单或设备序列号。

没有达到人数目标时，先根据实际反馈改善下载入口和启用解释，再调整自荐内容。保持同一版本的事实、校验信息和边界一致，不刷评、不用奖励交换好评。
