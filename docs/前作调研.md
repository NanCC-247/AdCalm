# 前作调研

这个项目不是凭空的。开工和校准过程中参考了以下项目与论文，这里记录**从每一处学到了什么、哪些采纳了、哪些刻意没采纳**，以及为什么。

写这份文档有两个用处：给使用者一个判断依据（该用这个还是用现成的），也给自己留个记录——避免以后重复踩同一个坑。

---

## GKD（搞快点）— 事实标准

[github.com/gkd-kit/gkd](https://github.com/gkd-kit/gkd)，GPL-3.0。

李跳跳 2023 年停更后的接棒者，目前最活跃的开源跳过广告工具。截至 2026 年 4 月，主流订阅覆盖 **863 个应用、超 3000 条规则**。

### 学到了什么

**1. 真实世界里的跳过按钮长什么样**

它的全局开屏规则是：

```
[text*="跳过"][text.length<10][width<500 && height<300][visibleToUser=true]
```

**这一行直接改进了本项目的打分表。** 我们原本要求文案**精确等于**「跳过」，导致「点击跳过」「跳过 >」「关闭弹窗」这类写法全部漏掉。当初要求精确匹配是为了挡住长正文里恰好含"关闭"的情况（真机日志里某个应用的隐私政策正文就含「关闭个性化广告推荐」）——但**用长度限制兜比用精确匹配兜覆盖面大得多**。

现在 `ConfidenceScorer` 里的 `isShortCloseText()` 就是这条的移植，长度上限 10 与 GKD 一致。

**2. 相对位置选择器**

GKD 的选择器支持 `+`（相邻兄弟）、`>`（子节点）等关系，例如：

```
'@View[text=null][clickable=true][childCount=0][width<200&&height<200] +(1,2) TextView[...]'
'@[clickable=true][height<100] - [text*="跳过"][text.length<10]'
```

**这个模式我们没有采纳。** 它的用途是处理"可点击元素和文字分处两个兄弟节点"的情况。而本项目的 `ClickExecutor` 是**从文字节点向上找可点击祖先**——父子关系的情况已经覆盖了，纯兄弟关系的情况相对少见。为它引入一套选择器语言，复杂度和收益不匹配。

如果以后发现大量漏点在"文字与点击目标真是兄弟"的场景，再回来看这条。

**3. 时序参数**

GKD 的规则带 `matchTime: 10000`、`actionMaximum: 1`、`resetMatch: 'app'`。

对照本项目：`ScanPolicy.SPLASH_WINDOW_MS = 8000`（开屏全速窗口）、`ClickCooldown` 的同元素冷却。**两边在关键参数上独立收敛到了相近的取值**，算是个正面的交叉验证。

**4. 规则分类与按需启用**

GKD 把规则分成「开屏广告 / 局部广告 / 全屏广告 / 分段广告 / 功能类」等类别，**默认只启用「开屏广告」**，其余要手动开。

本项目的对应取舍更保守：**默认一条规则都不带**（原因见下）。

### 刻意没采纳的部分

**没有采用它的规则库。**

两个理由，技术上的和合规上的：

- **技术**：没有证据表明按厂商 SDK 类名写的规则在本项目里有效。29 份真机节点树（400+ 节点，覆盖多个主流 App）里**零个广告 SDK 类名**。一个永远匹配不上的规则不是"无害的冗余"，它会让使用者误以为覆盖了若干广告平台。
- **合规**：一份标注了具体厂商广告 SDK 类名的规则文件，读起来就是一份"针对特定厂商广告"的靶向清单。本项目刻意不随代码分发这类内容——详见 README 的「分享与法律风险」一节。GKD 的多数订阅仓库自己也标着"禁止在国内平台传播"。

**想自己写规则的，请从你自己设备的诊断日志里得出**（流程见 `builtin.json` 里的 `_if_you_want_rules`）。

## 论文：Can We Stop The Ads?

[arxiv.org/abs/2609.17316](https://arxiv.org/abs/2609.17316)

系统梳理了开屏广告的形态和现有对抗手段。其中几个结论直接印证或修正了本项目的判断：

**1. "跳过"而不是"屏蔽"，在法律评价上是有区别的**

论文把开屏广告描述为"用户启动应用时弹出的全屏广告"，会诱使用户"在不知情的情况下触发某些机制"（比如晃动手机）从而跳转到第三方。

本项目从头到尾只做"找到屏幕上已经存在的按钮并点它"——不拦截请求、不改数据、不绕过技术措施。这不是免疫，但是一个实质性的区别。

**2. 现有工具的实际水平**

论文测试了 **11 个工具、13 种配置、10 个流行应用**，结论是：

> 只有 **1 个工具**能在全部 10 个应用里拦住广告触发的跳转，且该工具依赖无障碍权限，**广告在被关闭前会显示约 1 秒**。

这两条对本项目都很关键：

- **1 秒的延迟是行业现状，不是缺陷。** 我们的倒计时按钮确实是观测到数值递减后才点（约 1 秒），和最好水平持平。想更快只能靠"首次出现就点裸数字"，但那会把温度、角标之类的误判进来——收益不值这个风险。
- **"拦住广告跳转"是极少数工具才做到的事。** 本项目用哨兵 + 回退 + 强停专门解决这个，是相对少见的能力，也是它存在的理由。

**3. 部署障碍的普遍性**

论文指出多数方案要求 root、运行时注入或修改应用——即使避开这些，也还要附加权限、维护规则、编译源码或付费。

本项目选了"无 root + 本地判定 + 不联网"，代价是覆盖面明显不如 GKD。

## madeye/ad-skipper — 架构参考

[github.com/madeye/ad-skipper](https://github.com/madeye/ad-skipper)，MIT。

做的是同一件事，但检测分成三层：**节点匹配 → ML Kit OCR → YOLO11n 跳过按钮检测器**（约 5MB，ncnn + Vulkan）。

### 学到了什么

**1. 第三层是目标检测，不是文字识别**

本项目的 L3 用 ML Kit OCR 找"画出来的"关闭按钮，但 OCR 只认**文字**——遇到纯图形（倒计时圆环、没有文字的 ×）就没辙。YOLO 是训练出来的目标检测器，专门找"跳过按钮长什么样"。

**这是本项目目前的明确缺口。** 不过训练目标检测器需要标注数据，而本项目的真机样本还太少，暂时不做。

**2. 安全设计值得抄**

它的开屏窗口内轮询 + **每会话最多点 3 次**。本项目对应的是 `ClickCooldown` + `ScanPolicy` 的分档节奏，思路一致。

**3. 一个诚实的共同点**

它的文档明确写着：L3b（VLM 那一层）**只做过编译和 API 验证，端到端推理尚未实测**；训练和评测用的是合成数据，真实开屏广告的召回率"未系统验证"。

说明"没在真机上充分验证"是这个领域的普遍状态，不是本项目独有的问题。区别在于要把这件事**说清楚**，而不是含糊过去——README 的「真机验证状态」一节就是干这个的。

## 一句话总结

**如果你的目标是"尽可能多地跳过广告"，用 GKD**——它的规则库有社区维护的 863 个应用，这个数据优势本项目永远追不上。

**本项目存在的理由是另外两件事**：广告把你拽走之后能收拾干净（哨兵回退 + 强停），以及下载下来的安装包能拦下来。这两块 GKD 不做。
